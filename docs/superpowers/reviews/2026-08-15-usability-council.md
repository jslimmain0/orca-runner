# orca 러너 사용성 협의회 — 최종 로드맵

의장 확인: 7개 관점이 인용한 코드 근거를 전부 실측 검증했다(`src/add.ts`, `src/app.ts`, `src/cli.ts`, `src/supervisor.ts`, `src/config.ts`, `src/procctl.ts`, `src/health.ts`, `src/tui/*`, 설계 스펙·최종 리뷰 문서). 사실관계 오류는 없었다(한두 줄 수준의 줄번호 오차만 존재). 모든 채택 항목은 자원 예산(러너 CPU 1% / RAM 150MB)에 새 주기 작업을 추가하지 않는 범위로 한정했다.

---

## 1. 합의 요약

1. **가장 넓은 합의는 "안전"과 "진단 루프"였다** — 로그 뷰에서 `q` 한 번에 전체 서비스가 죽는 구조(TS-2, 4개 관점 top3)와, ERROR를 보고 `l`을 눌러도 로그가 비어 있는 막다른 길(ER-1, 2개 관점 top3)이 최우선 수리 대상이다.
2. **TUI 밖에서 상태를 볼 수 없는 구조가 사고를 만든다** — 자동화·신뢰안전 관점이 독립적으로 같은 결론(orca status 부재 + 세션 구분 없는 run.json)에 도달했고, "터미널 B에서 상태만 보려다 터미널 A의 서비스를 죽일 수 있다"는 시나리오는 실코드로 확인된 구조적 결함이다.
3. **반대가 집중된 곳은 "조용히 기본 동작을 바꾸는 편의"였다** — defaults.group(DD-4, 5개 관점 반대)과 TUI 내 임의 프로세스 kill(ER-5, 3개 관점 반대)은 예측 가능성·안전이라는 이 도구의 신뢰 계약과 상충해 기각한다.

---

## 2. 로드맵

작업량 표기: **소** = 반나절 이하, **중** = 1~2일.

### P0 — 지금 바로 (5개)

#### P0-1. `q` 안전화 + 종료 결과 리포트 `[TS-2, TS-1]` — 작업량: 소

- **무엇을**: ① 로그 뷰에서 `q`를 Esc/`l`과 동일한 "뷰 나가기"로 재매핑(app.ts:81의 `void quit()` 제거). ② 대시보드의 `q`는 **BUILDING/STARTING이 진행 중일 때만** 도움말 줄을 "q를 한 번 더 누르면 전체 종료 (빌드 진행 중)"로 바꿔 재확인을 받고, 그 외(UP뿐이거나 전부 DOWN/CRASHED/ERROR)에는 지금처럼 한 번에 종료. ③ `stopAll()`이 `{ stopped, timedOut }`을 반환하게 하고, 종료 마지막 줄에 "✔ 서비스 6개 모두 종료 확인" 또는 "⚠ 종료 미확인: eis-server (PID 12345) — 다음 orca 실행 시 고아 정리를 이용하세요"를 출력. killTree는 taskkill의 exit code를 구분해 '진짜 실패'만 이 목록에 반영.
- **왜**: TS-2는 유일하게 4개 관점(매일·설정인체공학·대시보드UX·신뢰안전)의 top3에 올랐다. less/git log 관용에 반하는 반사적 `q`가 몇 분짜리 빌드를 통째로 날리는 최악의 사고 벡터.
- **반대 해소**: 매일("퇴근 시 항상 UP이라 사실상 상시 확인")·에러상황("CRASHED로 뒤덮인 급박한 순간의 마찰") 반대를 수용해, 원안의 "UP이 하나라도 있으면 확인"을 **"빌드/기동 진행 중일 때만"으로 축소**하고, 평상시 안전은 확인창 대신 TS-1의 종료 후 리포트가 맡는다(매일 관점의 정제안 그대로). 대시보드UX가 지적한 SIGINT 우회 경로는 **의도적 예외로 확정**한다 — 외부 신호는 강제 종료 의사로 간주하고 확인을 생략하며, 이 결정을 코드 주석으로 명시한다.

#### P0-2. 빨간 상태 진단 3종 세트 `[ER-1, ER-2, ER-3]` — 작업량: 소

- **무엇을**: ① ERROR/CRASHED로 전이하는 **모든** 지점에서 `e.log?.close()` 전에 `[ORCA] <ISO시각> ERROR: <사유>`를 로그 마지막 줄에 기록하는 단일 헬퍼(writeExitReason) 도입 — 포트 점유(supervisor.ts:79-84), 스폰 실패(:117-121), 헬스 타임아웃, 그리고 CRASHED까지 동일 메커니즘. ② exit 핸들러가 `(code, signal)`을 받아 CRASHED에 `종료 코드 137` / `시그널 SIGTERM로 종료`를 error 필드로 세팅. ③ `httpUp()`을 `{ok, detail}` 반환으로 확장해 타임아웃 메시지를 "120초 내에 http://localhost:8081/actuator/health 확인 실패 (마지막: 연결 거부) — l로 앱 로그 확인"으로 구체화(health 미설정 시 "포트 8081 리슨 확인 실패"로 구분). ④ 대시보드 행이 폭 초과로 잘릴 때 마지막 문자를 `…`로 표시.
- **왜**: ER-1은 에러상황·대시보드UX 2개 관점 top3. "빨간 상태 → `l`"이라는 이 앱의 핵심 상호작용 루프가 현재 끊겨 있고, 설계 문서(:81, :122)가 명시한 "점유 PID를 로그에 남긴다"도 미이행 상태다. ER-2는 첫사용자 top3 — 2분을 기다린 사용자에게 단서 없는 메시지는 최악의 경험.
- **반대 해소**: 반대는 없었고, 대시보드UX의 정제안("ERROR만 고치면 CRASHED는 여전히 빈손 — 하나의 헬퍼로 묶어라")을 그대로 채택해 ER-1과 ER-3을 한 커밋으로 합쳤다.

#### P0-3. 대시보드 생동감 — 색상 + 경과 시간 + 헤더 스코프 `[DX-1, DX-2, DX-3]` — 작업량: 소

- **무엇을**: ① 상태별 ANSI 색(UP=녹색, STARTING/BUILDING=노랑, CRASHED=빨강, ERROR=마젠타, DOWN=dim). ② CRASHED='✖'/ERROR='!'로 아이콘 분리, tofu 위험이 있는 ◔/◐는 안전한 글리프로 교체. ③ ServiceState에 startedAt을 추가해 'BUILDING 42s' / 'STARTING 7s'를 표시 — 3초 tick마다 숫자가 바뀌어 renderDiff가 실제로 다시 그리므로 "멈춘 화면" 문제가 해소된다. ④ 헤더를 "시스템 CPU 12% · RAM 21.4/63GB"로 라벨링하고 statsOn일 때 "서비스 합계 {ΣrssBytes}MB" 병기(이미 수집 중인 값의 reduce라 추가 비용 0).
- **왜**: DX-2는 첫사용자·대시보드UX 2개 관점 top3, DX-1은 에러상황 top3. 콜드 빌드 중 "멈췄나?" 하고 강제 종료하는 위험이 실측 구조(renderDiff는 내용 불변 시 미갱신)로 확인됐다.
- **반대 해소**: 신뢰안전이 "색상만으로 BUILDING/STARTING 구분" 원안(③)에 반대(NO_COLOR·색약·파이프 환경에서 정보 소실) → **상태 텍스트 컬럼(padEnd(9))을 항상 유효한 폴백으로 유지하고 색은 가속 장치로만 쓴다**는 대시보드UX·에러상황의 정제안을 채택, 아이콘도 상태별로 서로 다르게 유지한다. 경과 시간 표기는 첫사용자("힌트는 0초부터")와 매일("분모는 소음")의 정제를 합성: **최초 빌드 진입 즉시** "(최초 빌드는 수 분 걸릴 수 있음)" 힌트, STARTING 분모(`/120s`)는 **30초 초과 후에만** 표기. ER-2(P0-2)와 같은 웨이브로 배포해 "대기 중 진행 표시 + 실패 후 진단"을 함께 완성한다(첫사용자 정제).

#### P0-4. `orca add` 인터뷰 전면 개선 — 즉시 검증 + 연속 등록 + 그룹 힌트 `[FR-1, FR-2, FR-4, CE-4]` — 작업량: 중

- **무엇을**: ① 이름/경로/포트를 입력 즉시 검증하고 실패한 필드만 재입력(포트 중복은 "포트 8081은 이미 eis-server가 쓰고 있습니다"처럼 점유 서비스명 명시, 프롬프트에 예시 인라인). ② 등록 완료 후 "다른 서비스도 등록할까요? [y/N]" 루프 — 회차 헤더에 "[2번째 서비스]" 표시, 종료 시 "이제 'orca'로 대시보드를 실행해 확인하세요" 안내. ③ 그룹 질문에 기존 그룹 목록 노출("그룹 (없으면 엔터, 기존: tspay, infra): "), trim + 대소문자만 다르면 "'Tspay' 대신 기존 그룹 'tspay'를 쓸까요? [Y/n]" 통일 확인. ④ 안전망 보강: config.ts의 loadConfigFromString에도 이름 정규식 검사를 fail() 패턴으로 추가(YAML 직접 편집 경로 방어).
- **왜**: FR-1(첫사용자 top3)·FR-2(설정인체공학 top3). 사내 서비스 6개를 등록하는 이 페르소나가 마지막 질문에서 실패해 7개 답변을 통째로 날리고 `orca add`를 6번 재실행하는 것이 첫 10분 경험의 최대 마찰. CE-4는 FR-1과 동일 제안이라 통합.
- **반대 해소**: 반대는 없었고 정제 2건을 필수 요건으로 채택 — **중복 검사·그룹 힌트의 기준 config는 세션 시작 캐시가 아니라 루프 회차마다 CONFIG_PATH를 재로드**한다(첫사용자·설정인체공학 공통 지적: 회차마다 즉시 저장되므로 캐시 참조 시 "방금 등록한 서비스와의 충돌을 못 잡는" 구멍이 생긴다).

#### P0-5. `orca status [--json]` + 세션 소유 구분 `[TS-4, AU-1, AU-5]` — 작업량: 중

- **무엇을**: ① TUI 없이 run.json + isAlive + portListening/httpUp으로 실제 상태를 판정해 `eis-server   UP     :8081  pid 12345` 형태로 출력하고 즉시 종료하는 조회 전용 서브커맨드(전부 UP=exit 0, 아니면 1). `--json`으로 기계용 배열 출력(같은 판정 로직, 직렬화만 분기). ② run.json에 **소유 세션 PID**를 함께 기록하고, findOrphans가 정리 프롬프트 전에 소유 세션 생존을 확인 — 살아 있으면 "이미 다른 터미널(PID nnnn)에서 관리 중입니다. 상태만 보려면 orca status를 쓰세요"로 안내하고 프롬프트를 띄우지 않는다.
- **왜**: TS-4(자동화 top3)와 AU-1(신뢰안전 top3)이 **독립적으로 동일한 결론**에 도달한 유일한 항목. "상태 확인이라는 정상 행동 → 다른 세션 서비스 전멸"은 현재 코드에서 재현 가능한 사고 경로이며(findOrphans는 isAlive만 확인, y 한 번에 taskkill /T /F), 사용성 문제이자 안전 문제다. 1회성 실행 후 종료라 자원 예산 영향 없음.
- **반대 해소**: 직접 반대 없음. 자동화 관점의 정제(--json을 처음부터, exit code 계약을 텍스트/JSON 동일 유지)와 에러상황의 정제(소유자가 죽어 있어도 일괄 y/N로 회귀하지 말 것 — 개별 선택 UI는 P2의 TS-3에서 완성하되, 그 전까지는 목록에 포트·응답 여부를 병기)를 반영했다.

## 4. 관점 간 쟁점과 의장 판단

**쟁점 1 — 종료 확인: 안전장치인가 마찰인가.**
신뢰안전·대시보드UX는 확인 절차를(top3로), 매일·에러상황은 매일의 정상 종료와 급박한 탈출에 마찰이 없기를 요구했다. **판단**: 두 진영 모두 옳다 — 다만 층위가 다르다. 실제 사고 벡터(로그 뷰의 반사적 `q`)는 확인이 아니라 **재매핑으로 원천 제거**하는 것이 맞고, 확인창은 "잃으면 손해가 큰 순간"(빌드/기동 진행 중)에만 남긴다. 평상시 안전은 사전 확인이 아니라 **종료 후 결과 리포트**(무엇이 안 죽었는지)로 옮긴다. 마찰 0에 가깝게 유지하면서 두 관점이 각각 지목한 사고(반사적 q, 침묵하는 stopAll)를 모두 막는 구성이다.

**쟁점 2 — 인자 없는 `orca`의 의미.**
매일 관점은 반복 타이핑 절감을, 나머지 4개 관점은 "인자 없으면 전부"라는 계약의 보존을 주장했다. **판단**: 기본값을 조용히 바꾸는 편의는 이 도구가 다른 곳(FR-4, CE-3)에서 싸우고 있는 "조용한 누락"을 CLI 레벨에서 재생산한다. 기각하고, 타이핑 절감은 alias·세션 재개·그룹 목록 안내라는 명시적 수단으로 해결한다. 원칙: **orca에서 보이는 것의 범위는 항상 명령줄에 드러나야 한다.**

**쟁점 3 — 서브커맨드 확장 vs 그룹 이름공간.**
자동화·설정인체공학은 status/up/down/start/stop/remove/edit/groups 확장을 요구했고, 매일·설정인체공학(자기 발의에 대한 자기 견제 포함)은 "위치 인자 하나가 서브커맨드와 그룹명을 겸하는 구조에서 예약어가 9개로 늘면 사용자가 지은 그룹명이 조용히 다른 뜻이 된다"고 경고했다. **판단**: 확장의 가치(TUI 밖 제어·조회는 이번 협의회의 2대 합의 중 하나)가 커서 수용하되, **이름공간 정책을 P1-1로 선행**시킨다 — 예약어 목록 고정·문서화, add에서 예약어 그룹명 즉시 거부, 기존 충돌 그룹은 경고와 함께 서브커맨드 우선. 그리고 첫사용자의 경고대로 `--help`는 "첫 10분 경로"와 "자동화 명령"을 섹션으로 분리해, 명령이 늘어도 처음 켠 사람의 길은 세 줄로 유지한다.

*P0 5개는 전부 렌더 문자열·검증·1회성 실행 수준의 변경으로, 새 주기 작업이 없어 자원 예산(CPU 1% / RAM 150MB, 실측 0.05~0.26% / 146MB)에 영향을 주지 않는다. P1-4의 포트 확인만 기존 3초 tick에 편승하는 TCP connect가 추가되며 이 역시 예산 내다.*
