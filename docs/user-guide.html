orca 사용자 가이드

orca는 로컬 개발에 필요한 사내 서비스들을 자원을 아껴서 백그라운드로 띄워주는 Windows 전용 터미널 도구입니다.

핵심 아이디어는 하나예요: 지금 고치고 있는 서비스는 IDE로 띄우고, "떠 있기만 하면 되는" 나머지는 orca에 맡긴다. orca는 맡은 서비스를 힙 제한·코어 제한·낮은 우선순위로 실행해서, 6개를 동시에 띄워도 컴퓨터가 버벅이지 않게 합니다.

1설치

저장소에서 한 번만:

pnpm install
pnpm build
npm install -g .        # 이후 어느 폴더에서든 `orca`

업데이트했을 때도 같은 명령을 다시 실행하면 됩니다.

2첫 10분

orca setup     # ① 최초 1회 튜닝
orca add       # ② 서비스 등록 (대화형)
orca           # ③ 대시보드 실행 → a 키로 전체 시작

① orca setup — Windows Defender 실시간 검사 예외에 프로젝트 폴더·Gradle 캐시·pnpm 스토어를 등록합니다(관리자 권한 창이 한 번 뜹니다 — 빌드 속도와 상시 CPU 사용에 크게 영향). Java/Node 버전과 JAVA_HOME도 점검하고, 각 프로젝트의 gradle.properties에 권장 사항이 있으면 안내만 합니다(파일을 고치지는 않음).

② orca add — 질문에 답하면 서비스가 등록됩니다. 잘못 입력하면 그 항목만 다시 물어보고, 하나 끝나면 "다른 서비스도 등록할까요?"로 이어서 등록할 수 있어요.

③ orca — 대시보드가 뜹니다. a를 누르면 등록된 서비스가 순차적으로 빌드·기동됩니다(동시 빌드로 CPU가 폭주하지 않도록 일부러 순차).

3서비스 등록

두 가지 종류

kind대상orca가 하는 일
springGradle 기반 Spring Boot 프로젝트gradlew bootJar로 jar를 빌드(소스가 안 바뀌면 캐시 재사용)한 뒤 java -jar를 힙 512MB 제한 + 2코어만 인식 + SerialGC + 낮은 우선순위로 실행. 빌드에 쓴 Gradle 데몬도 자동 정리
command그 외 전부 (스크립트, 정적 서버 등)등록한 명령을 낮은 우선순위로 실행. cpus를 명시하면 CPU affinity 제한도 적용

설정 파일 직접 편집

등록 내용은 전부 %USERPROFILE%\.orca\services.yaml 한 파일에 있습니다. 직접 편집해도 되고, 대시보드가 떠 있는 동안 저장하면 자동으로 반영됩니다(핫로드 — 6절).

defaults:
  spring:
    heapMb: 768            # 전역 기본값 덮어쓰기 (기본 512)

services:
  eis-server:
    group: tspay           # 그룹 (orca tspay 로 묶어서 실행)
    kind: spring
    dir: C:\work\EIS
    module: eis-server     # 멀티모듈이면 모듈명 (단일 모듈이면 생략)
    port: 8081
    health: http://localhost:8081/actuator/health
    heapMb: 1024           # 이 서비스만 힙 1GB
    jvmArgs:
      - -Dspring.profiles.active=local
    env:
      PG_PORT: 5432          # 숫자도 됨 — 문자열로 자동 변환
  legacy-gateway:
    kind: command
    dir: C:\work\gateway
    run: run-local.cmd
    port: 9000

필드 레퍼런스

필드필수설명
kind✔spring 또는 command
dir✔프로젝트 절대 경로 (C:\...)
port✔서비스 포트 (1~65535, 서비스 간 중복 불가)
runcommand만 ✔실행할 명령
modulespring 멀티모듈의 대상 모듈
health헬스체크 URL. 없으면 포트 리슨 여부로 UP 판정
group묶음 이름. 예약어(add setup status up down start stop remove groups advise help)는 사용 불가
heapMb metaspaceMb cpus priority jvmArgs자원 제한 오버라이드. priority는 normal / belowNormal / idle
env서비스별 환경변수 맵. 셸 환경 위에 덮어씀. 숫자/불리언 값은 문자열로 자동 변환

서비스 이름은 영문/숫자/. _ -만 가능합니다(로그 파일명으로도 쓰이기 때문).

등록 해제는 orca remove [이름] — 이름을 생략하면 번호 목록에서 고릅니다. 실행 중인 서비스는 해제할 수 없어요(먼저 orca stop <이름>).

로그 뷰 안에서 q는 종료가 아니라 대시보드 복귀입니다. 습관적으로 눌러도 서비스가 죽지 않아요.

빨간 상태가 보이면 l을 누르세요. 모든 ERROR/CRASHED의 사유는 로그 파일 마지막 줄에 [ORCA] <시각> ERROR: <사유> 형태로 항상 남습니다.

세션 재개

q로 종료하면 그 순간 어떤 서비스가 떠 있었는지 기억합니다. 다음에 orca를 실행하면:

 지난 세션: 4개 실행 중이었음 — [u] 재개 / 실패했던 서비스: security (l로 사유 확인)

u 한 번으로 어제의 세팅이 그대로 돌아옵니다. (CRASHED/ERROR로 끝났던 서비스는 자동 재개에서 빠지고 안내만 — 실패를 매일 아침 반복하지 않기 위해서예요.)

5TUI 밖에서 쓰기 (자동화)

모든 명령은 성공 0 / 실패 1의 exit code 계약을 지키므로 스크립트에서 바로 쓸 수 있습니다.

orca status              # 상태 표 출력. 전부 UP이면 exit 0
orca status --json       # 같은 판정을 JSON으로

orca up                  # 지난 세션 재개 (이미 떠 있는 건 그대로 성공 — 멱등)
orca up tspay            # 그룹만
orca up --all            # 전체

orca down                # 종료 "대상 목록만" 출력 (dry-run)
orca down --yes          # 실제 종료
orca start eis-server    # 개별 시작
orca stop eis-server     # 개별 종료

orca advise               # 사용량 기반 heapMb/metaspaceMb 추천 (9.5절)

headless(up/start)로 띄운 서비스는 CLI가 끝나도 계속 돌고, orca status로 확인하고 orca down --yes로 정리합니다.

소유 세션 보호 — 어떤 서비스를 어느 orca가 관리하는지 기록되기 때문에, 다른 터미널의 대시보드가 관리 중인 서비스를 orca down이 죽이지 못합니다("그 터미널에서 종료하세요"로 거부). 반대로 대시보드를 새로 열 때 다른 세션이 이미 돌고 있으면 안내만 하고 건드리지 않아요.

6설정 핫로드

대시보드가 떠 있는 동안 services.yaml이 저장되면 자동으로 반영됩니다 — 직접 편집이든, 다른 터미널에서 실행한 orca add/remove든 마찬가지입니다.

변경반영
서비스 추가DOWN 행으로 즉시 나타남
꺼져 있는 서비스 삭제목록에서 즉시 사라짐
실행 중인 서비스 삭제(설정에서 삭제됨 — 중지 시 제거) 표시로 계속 관리하다가, 중지하면 사라짐
설정 값 변경 (힙, 포트 등)실행 중이면 ⟳ 설정 변경 — r로 반영 표시만. r로 재시작하면 새 설정 적용
파일이 깨짐기존 설정 유지 + ⚠ services.yaml 오류 배너. 파일을 고치면 배너가 사라짐

실행 중인 프로세스는 어떤 경우에도 orca가 마음대로 재시작하거나 죽이지 않습니다.

7문제 해결

! ERROR 포트 8081 점유 중: java.exe (PID 1234)

그 포트를 누가 쓰고 있어요. IDE에서 직접 띄운 내 서비스라면 → orca에서 그 서비스를 x(SKIP)로 표시하는 게 정답입니다. 모르는 프로세스라면 PID로 확인 후 정리하세요.

! ERROR 120초 내 ... 확인 실패 (마지막: 연결 거부)

프로세스는 떴는데 헬스체크를 통과하지 못했어요. l로 앱 로그를 확인하세요 (DB 연결 실패 등 앱 자체 문제인 경우가 대부분). orca는 이때 프로세스를 정리해 좀비를 남기지 않습니다.

× CRASHED 프로세스 종료 (code 1)

서비스가 스스로 죽었습니다. l → 마지막 로그에서 원인 확인. 자동 재시작은 일부러 하지 않아요(원인 파악을 방해하니까). 고친 뒤 s나 r로 다시 시작.

빌드 실패

! ERROR 빌드 실패: ... → l을 누르면 Gradle 빌드 로그가 그대로 보입니다.

"이전 세션이 남긴 프로세스가 있습니다"

orca가 비정상 종료(터미널 강제 닫기 등)됐을 때 남은 프로세스입니다. 각 항목의 포트·응답 여부를 보고 y로 정리하면 됩니다.

종료했는데 ⚠ 종료 미확인이 떴다면

드물게 프로세스가 5초 안에 안 죽은 경우입니다. 다음 orca 실행 시 고아 정리 프롬프트가 잡아줍니다.

알려진 한계

  • command 서비스의 MEM/CPU 표시는 cmd 래퍼 프로세스 기준이라 실제보다 작게 보일 수 있음 (spring은 정확)
  • command의 cpus(affinity)는 명시했을 때만, 현재는 래퍼 프로세스에 적용
  • headless로 띄운 서비스는 대시보드가 "이어받지" 못함 — 대시보드에서는 포트 점유로 보이므로, headless 것은 orca down으로 관리

8파일 위치

전부 %USERPROFILE%\.orca\ 아래에 있습니다:

파일내용
services.yaml서비스 등록 (직접 편집 가능, 핫로드됨)
logs\<이름>.log서비스별 로그 (10MB 넘으면 .1로 롤링)
run.json실행 중 프로세스 기록 (소유 세션 포함 — 직접 편집 비권장)
last-session.json마지막 세션 스냅샷 (재개 기능용)
cache.jsonspring jar 빌드 캐시
usage.json서비스별 사용량 누적 (RSS/힙/메타/FGC — 사용량 추천용, 9.5절)

9자원 사용에 대해

orca 자체는 평균 CPU 1% 이하, RAM 150MB 이하 예산으로 설계·실측됐습니다(수집 헬퍼 포함). 자원 수집은 3초에 한 번 전체를 일괄 샘플링하는 PowerShell 헬퍼 1개가 전담하고, m으로 끄면 그 헬퍼조차 종료됩니다. 직접 재측정하려면:

pnpm build; node scripts/measure-budget.mjs

9.5사용량 추천

spring 서비스를 돌릴 때마다 RSS·힙·메타스페이스·Full GC 사용량을 ~\.orca\usage.json에 누적합니다(대시보드 종료 시 저장). 세션이 쌓이면 대시보드 행에 이렇게 뜹니다:

 3 ● core-api        : 8080 UP                420MB   1%
   ▼ 권장: 힙 512→256·메타 256→128 ([v] 적용)
  • 상향(위험 신호): 힙 사용률 90% 초과 또는 Full GC가 세션평균 20회 넘게 발생 → 1회 관측만으로도 즉시 표시. 메타스페이스는 사용률 85% 초과 시 즉시.
  • 하향(여유 있음): 힙 35% 미만, 메타 40% 미만인데 세션 2회 이상 관측됐을 때만(단발성 저사용으로 섣불리 줄이지 않기 위함).
  • v를 누르면 선택한 서비스의 heapMb/metaspaceMb를 services.yaml에 즉시 반영하고(주석은 보존), 실행 중이었다면 자동으로 재시작합니다. 적용한 항목은 그 세션 동안 다시 뜨지 않습니다.
  • command 서비스는 래퍼 프로세스라 측정 정확도가 떨어져 추천 대상에서 제외됩니다(행 표시도 안 됨).
  • 대시보드 밖에서 한눈에 보려면: orca advise — 서비스별 현재 설정·관측치·권장값을 표로 출력합니다(실행 중이면 현재 jstat 값도 병기).
